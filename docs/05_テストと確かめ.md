# 05 テストと確かめ

## テストの段

| 段 | コマンド | 何を試すか | 本数 |
|---|---|---|---|
| 単体テスト(DBなし) | `npm test` | 「次の人へ」の要約・話す順のヒント・入力秒数の集計・日本時間の日付(年またぎ含む)・カナの揃え方・保存前の入力チェック(ない日付・長さ・送信ID)・seed の接続先の確認 | 42本 |
| 統合テスト(実DB) | `npm run test:db` | 年またぎの来店予定・同時に「済み」・同時に記録・二重送信(順番/同時)・記録時点の役割・見本と実測の分離・店の境界・トランザクションの巻き戻し・DBの制約 | 16本 |
| 画面の通しテスト | `npm run test:e2e` | iPhone 13 の大きさの画面で、イベントスタッフが記録 → 常勤が続きから記録/スタッフ未選択では保存できない/二重登録の候補表示 | 3本 |
| 静的チェック | `npm run lint` / `npm run typecheck` | ESLint・TypeScript strict | - |
| build | `npm run build` | DBにつながらない状態でも通る | - |

CI(`.github/workflows/ci.yml`)で全部を流す。DBを使うテストは GitHub Actions のサービスとして PostgreSQL 17 を立てる。
**CI は GitHub ではまだ動かしていない**(push していないため)。代わりに、ローカルで素の `postgres:17` を立てて、同じ手順(migrate deploy → seed → 統合テスト)が通ることを確かめた。

## 主に確かめたことと、確かめ方

### 30秒以内
- 画面を開いてから保存までの秒数を `visits.input_seconds` に保存している
- 集計(平均・中央値・30秒以内の割合)は関数にして、0件・おかしな値を含めて単体テストした
- 今日の一覧に、直近30日の「平均/30秒以内の割合」を全体・常勤・イベントに分けて出す
- 集計は人が画面で入れた記録(source=MANUAL)だけ。見本(SEED)と自動テスト(E2E)は入れない(統合テスト)。見本の秒数は「見本値(参考)」と分けて出す(画面テスト)
- **まだ確かめていないこと**:本物の人が30秒で入れられるか。自動テストは速すぎて0〜1秒で保存する。次はスタッフに使ってもらって数字を見る

### 誰が案内したか必ず残る
- DB:`visits.staff_id` は NOT NULL
- サーバー:「今のスタッフ」が選ばれていなければ保存を断る
- 画面:保存ボタンが押せない(画面テスト)
- スタッフを切り替えたとき、要約に出る人が正しく替わることを画面テストで確かめた(森田 → 高橋)

### 2回目の人が最初の説明をしなくて済む
- 画面テストで、実際の要約の文「前回 … 森田 陽菜(イベント)が「のりかえ(MNP)」で 料金比較・端末価格 まで案内済み。次は 下取り・キャンペーン から。」と、2回目の記録のあとに「次は」が正しく進むことを確かめた
- 前々回に案内した項目は「次は」に再び出さない(単体テスト)

### 年またぎ(時間が進むもの)
- 単体:12/31 23:59:59 は2026年、0:00 は2027年。12/31(木)の「今週」は 12/28〜1/3。うるう年・月末をまたぐ日数の足し算
- 統合:12/29 に「1/2 来店予定」と記録し、4つの時点で一覧を見る
  - 12/30 → 今週 / 1/1 0:00 → 今週 / 1/2 → 今日 / 1/4・12/27 → 出ない

### 同時に動いたとき
- **競合しそうな所(先に予告)**:① 同じ「次にやること」を2人が同時に済みにする ② 同じお客様に2人が同時に記録する ③ 同じ新規のお客様を2人が同時に登録する ④ 同じ記録の二重送信
- ①:`done_at` が空のときだけ更新する。統合テストで2つ同時に投げ、1つだけ通り、済ませた人が正しく残ることを確かめた
- ②:記録は別々の行に入るので、どちらも消えない。統合テストで両方残ることを確かめた
- ④ 保存を2回押す・同じ送信が同時に2つ届く:送信IDの一意制約で1件にまとめる。順番に2回・同時に2回の両方を統合テストで確かめた(3回続けて流して安定)
- ③:**防げていない**。一意制約を付けていない(理由は 03)ので、重複したお客様ができうる。新規入力中にカナと下4桁が合う登録済みのお客様を候補に出し、タップで選び直せるようにした(画面テストあり)。ただし2人が同じ瞬間に新規登録したら二重になる。重複をまとめる機能は次の段階

### 店の境界
- 別の店のスタッフでは記録できない/別の店のお客様には記録できない/別の店のスタッフは「済み」にできない、を統合テストで確かめた。DBでは保証していない(03)

### seed の保護
- 接続先が localhost 以外なら止まる(単体テスト+実際に外のURLを渡して止まることを確かめた)

### DBの制約
- 選んでいない用件の項目のチェック・数字4つでない下4桁・漢字の混ざったカナ・自由記入なしの「その他」を、それぞれDBが弾くことを統合テストで確かめた
- 保存の途中で失敗したら、新規のお客様も作られない(1つのトランザクション)

### インデックス
- トランザクションの中で2万人入れ、`EXPLAIN ANALYZE` で実行計画を見てから取り消した(詳しくは 03)

### Supabase の API から読めない
- 公開キーで `/rest/v1/customers` を読むと空の配列が返る(RLS が効いている)
