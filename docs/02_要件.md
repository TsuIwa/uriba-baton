# 02 要件

もとになった話は [01_ヒアリング.md](01_ヒアリング.md)。

## 誰の、何の困りごとか

| 誰が | 何に困っているか |
|---|---|
| 2回目に来たお客様 | 前回聞いた説明を、もう一度最初から聞かされる |
| 2回目のお客様を受けるスタッフ | 前回だれが・どこまで案内したか分からない。何から話せばいいか分からない |
| 臨機応変が苦手なスタッフ | 前回の記録がないと止まってしまう |
| 週末のイベントスタッフ | 忙しく、案内が「さっくり」になる。書く手間が増えると記録しなくなる |

原因は3つ。

1. 記録が紙のメモなので、探せない・残らない
2. **誰が**案内したかが残らない
3. **どこまで**案内したかが分からない

## 完成の基準

| 基準 | 確かめ方 |
|---|---|
| 30秒以内で記録できる | 最初の入力から保存までの秒数を毎回保存し(画面を開いたまま接客する時間は混ぜない)、今日の一覧に平均と「30秒以内の割合」を出す。集計は人が画面で入れた記録だけ(見本・自動テストは除く)。**現場の人での計測はまだ**なので、この基準はまだ満たしたと言えない |
| 誰が案内したか必ず残る | 記録の担当者は画面上部の「今のスタッフ」から自動で入る。DBでも NOT NULL。スタッフを選ばないと保存ボタンが押せない |
| 2回目の担当者が最初の説明をしなくて済む | お客様カードの一番上に「前回◯◯さんが△△まで案内済み。次は□□から」を出す。その下に話す順のヒントを3つまで出す |

## やること(この版)

- **30秒の記録**:お客様を探す/新規 → 用件(複数可)→ 案内したこと → 温度感 → 次にやること → 次回来店予定(任意)→ 保存。すべてタップで選べる。自由記入(メモ・「その他」の中身)は任意
- **入力秒数の記録**:最初の入力(タップ・文字入力)から保存までの秒数を保存し、平均・中央値・30秒以内の割合を出す(常勤/イベントで分けて見られる)
- **お客様カード**:名前カナ・電話番号の下4桁で探す。開くと「次の人へ」の要約 → 話す順のヒント → 過去の記録の時系列
- **今日の一覧**:今日・今週の来店予定のお客様と、終わっていない「次にやること」
- **イベントスタッフの印**:記録・一覧で、イベントスタッフが案内した記録には印をつける
- **スマホ縦が主**:ボタンは高さ48px以上、保存ボタンは画面下に固定

## 引き継ぎのルール(現場の判断。原文は 04)

| 場面 | 次の人に出すこと |
|---|---|
| 「見積もりを渡す」がまだ | 見積もりを作りながら詳細を案内する(声かけの例つき)。感想は聞かない |
| 「見積もりを渡す」が済んだ | お渡しした見積もりの感想から聞く |
| 前回より前の約束が未完了のまま | 済んでいるか、その記録の担当者に確認してから進める |
| 説明済みの項目 | 期限で切らない。まず理解度を伺い、必要ならもう一度詳しく |
| 前回「理解があいまい」だった項目 | もう一度詳しく案内 |
| 料金・キャンペーンなどで、前回の説明のあとに中身が変わった | 必ず案内(説明済みに数えない) |

**誰が「中身が変わった日」を入れるか**:店長が、料金プランやキャンペーンが変わった日に入れる想定。**入れる画面はこの版では作っていない**。見本データでは「キャンペーンは seed を流した日の6日前に変わった」として入れている(2026-10-07 に流すと 10/1)。

## やらないこと(この版)と、その理由

| やらないこと | 理由 | 次の段階でどうするか |
|---|---|---|
| ログイン認証 | この版は**ローカルで動かす見本**。画面の流れとDB設計を先に固めた。**現場で試す前には必ず入れる** | Supabase Auth でスタッフごとにログインし、「今のスタッフ」をログインした人に置き換える。あわせて店舗単位の認可(ログインした人の店のデータだけ読む・書く)を入れる |
| お客様の氏名(漢字)・電話番号の全桁 | 引き継ぎに必要なのは「同じ人だと分かること」だけ。個人情報は最小限にする | 増やさない方針。必要になったら理由を書いてから足す |
| AIによる要約 | 同じ記録なら毎回同じ文が出る方が、現場で信用しやすく、説明もできる | 記録がたまったら、ルールの要約とAIの要約を並べて比べる |
| 複数店舗 | まず1店で使ってもらう | テーブルは `store_id` を持っているが、**画面を足すだけでは済まない**。①ログインした人の店を決める認可 ②今は「最初の店」を固定で読んでいる所の置き換え ③DBで保証していない店の一致(記録のスタッフとお客様が同じ店か、など。03 に書いた)をDBでも守るか決める、が要る |
| 改定日を入れる画面 | まず「変更あり」の出し方を固めた | 店長だけが入れられる画面(ログインと権限のあと) |
| 記録の修正・削除 | 「誰がいつ何をしたか」を残すことを優先した | 修正は履歴を残す形で足す |
| 外部への公開・デプロイ | 公開前に、持ち主の確認が要る | Vercel + Supabase(本番)へ。手順は README の「今後の改善」 |

## 認証が無いことで、今守れていること・守れていないこと

| | 守れている | 守れていない |
|---|---|---|
| Supabase の API(公開キー) | RLS を有効にしてポリシーを作っていないので、API から表を直接読み書きできない | - |
| このアプリの画面・サーバーアクション | 画面から届く値はサーバーで確かめる。スタッフ・お客様・次にやることが「この店のもの」かは関数で確かめる | **アプリのURLに届く人は、誰でも全部のお客様を読めて、記録できる**。「今のスタッフ」も誰でも選べる |

このため、この版はローカルで動かす見本にとどめる。現場で試す前にログインと店舗単位の認可を入れる。
