# 04 AIとの作業記録

この作品の実装は、制作者が Claude Code(コードを書くAI)に頼んで進めた。
何を頼み、AIが何をして、どこで直したか・決めたかを書く。誇張せず、あったことだけを書く。

## 誰が何を決めたか

| こと | 決めた人 |
|---|---|
| ヒアリングの問いと読み取り(01) | 制作者 |
| 作るもの(機能の一覧・完成の基準・やらないこと・DBは正規化した複数テーブル・電話番号は下4桁) | 制作者が依頼文に書いた |
| テーブルの細かい形・制約・画面の並び・要約とヒントのルールの文面 | Claude Code が案を出して実装した。理由は 03 に書いた |
| 公開・GitHubへのpush・デプロイ | まだしていない(制作者が確認してから) |

## 作業の流れ(2026-10-06、時系列)

### 1. 今の版の書き方を確かめた
- Prisma 7 は 6 から書き方が変わっているので、公式ドキュメント(v7)を読んでから書いた(generator は `prisma-client` で `output` 必須、接続先は `prisma.config.ts`、クライアントはドライバーアダプター `@prisma/adapter-pg` 経由でつなぐ)
- Next.js 16 は `node_modules/next/dist/docs` の同梱文書で確かめた(`params`・`searchParams`・`cookies()` は await でしか読めない)
- Docker を起動して `supabase start` でローカルの Supabase を動かした。SQLite に逃げる必要はなかった

### 2. 部品同士のぶつかり
- Vitest を入れるとき、ひな形が入れていた `@types/node@20` と求める版がぶつかって入らなかった → **直した**:`@types/node` を Node 24 系に上げた(CI の Node の版にも合わせた)

### 3. DB設計
- 9テーブルで設計。判断を1つ足した:チェック項目の中間表は、**組の外部キーで矛盾をDBが止める**形にした(理由は 03「迷った所 3」)
- 最初の案では `visit_checks` から `visits` への外部キーも直接張っていたが、`visit_topics` 経由で守れている内容と同じなので、マイグレーションを流す前に**外した**
- CHECK 制約と RLS は Prisma のスキーマに書けないので、マイグレーションの SQL の末尾に手で足した

### 4. ロジックとテスト
- 要約・ヒント・入力秒数の集計・カナの揃え方・保存前のチェックは、画面から切り離した関数にして単体テストを書いた
- 「今日」「今週」は日本時間で決めるようにし、年またぎ(2026-12-31 → 2027-01-01、12/28〜1/3 の週)のテストを入れた
- 実DBを使う統合テスト(10本)で、年またぎの来店予定と、同時に「済み」を押したときを確かめた。**1回目で全部通った**

### 5. 画面と通しテスト
- Playwright の通しテストは1回目に失敗した。原因は**テスト側の書き方**で、リンク名「お客様」が「このお客様の記録を残す」にも当たっていた → 完全一致で探すように直した
- スクショを見て、今日の一覧の「次にやること」が28件縦に並んで長かったので、**古い順8件だけ見せて残りは開く形に変えた**

### 6. 書いた文書と実装の食い違い
- 05 に「画面で二重登録の候補を見せる」と書いたが、新規入力の画面にはまだ無かった → **直した**:新規入力中にカナ+下4桁が合う登録済みのお客様を候補に出す機能と、その画面テストを足した
- 04 と 05 を一度英語で書いてしまった → 日本語で書き直した

### 7. DBなしで build が落ちた
- CI を想定してDBなしで `npm run build` したら落ちた。レイアウトが「動的に描く」と決まる前にDBを読んでいたため、build 時に先読みしようとしていた
- **直した**:レイアウトの先頭で `connection()` を呼び、必ずリクエスト時に描くようにした。DBなしでも build が通ることを確かめた

### 8. インデックスを確かめたときの回り道
- お客様20人ではDBが索引を使わない方を選ぶので、トランザクションの中で2万人入れて実行計画を見てから取り消した
- **分かったこと**:カナだけの前方一致が全件読みになっていた(照合順序のせいで普通の索引が使えない)
- `varchar_pattern_ops` を Prisma のスキーマに書いたら効いたが、**Prisma 7.10 はその索引を作り直すマイグレーションを毎回出し続けた**
- ここでローカルDBを作り直そう(reset=全消し)としたら、**Prisma が「全消しは利用者の同意が要る」と止めた**。同意は取っていないので、**reset はしなかった**
- **最後の判断**:適用済みのマイグレーションはそのまま残し、スキーマ側の索引は素の形で書いて注記した。Prisma が差分なしと見ることを確かめた(`migrate status` で問題なし)。CHECK 制約と同じく「Prisma で書けないものはSQL側で持つ」形にそろえた
- 試しの途中でできたマイグレーション2つ(適用済み1つ・空1つ)は、消さずにプロジェクトの外へ移した。適用済みの方は正式なマイグレーションとして戻した

### 9. 面接官役の審査で指摘されたこと → 直したこと
別のAI(Codex)に面接官役をさせて作品を審査し、指摘を受けた。業務の判断が要る3件(話す順のヒントの文の矛盾・前々回の未完了の約束が消える・説明済みを全履歴で数えている)は**制作者に聞いてから直すので、今回は触っていない**。技術面の指摘は次のように直した。

| 指摘 | 直したこと |
|---|---|
| 見本データの作り物の秒数が、実測のように平均されている | `visits.source`(人/見本/自動テスト)を足し、画面の集計は人の分だけに。見本は「見本値(参考)」と分けて表示。実測0件なら「まだ実測なし」。README の冒頭に「30秒は目標。現場の人での計測はまだ」と書いた |
| 保存の二重送信で記録が2件になる | 記録画面を開いたときに送信IDを作り、`visits.request_id`(一意制約)に保存。同じIDの再送は保存済みの1件を返す。同時に2つ届く場合も含めて統合テスト |
| 入力チェックがDBとずれている | カナの長さをDBと同じ60文字に。ない日付(2027-02-30)を断る。メモ・「その他」は黙って切らずに長すぎると伝える。エラーは「お客様:」「次回来店予定:」のように欄の名前から始め、どう直すかまで書く |
| 役割を変えると過去の集計と印が変わる | `visits.staff_role_at_visit` を足し、印・集計・要約はそれを使う(03「迷った所 4」を書き直した) |
| seed が接続先のDBを確かめずに全部消す | localhost 以外なら止める。消すのと入れるのを1つのトランザクションに |
| 「複数店は切り替え画面を足すだけ」は言い過ぎ | 02 を直した。記録のスタッフ・お客様が同じ店か、済みにする人がこの店のスタッフかを関数で確かめ、統合テストを足した。DBで保証していない部分は 03 に書いた |
| 認証が無いことの説明が足りない | README と 02 に「ローカルの見本。現場で試す前にログインと店舗単位の認可を入れる」と、RLS が守る範囲・守らない範囲を書いた |
| ヘッダーの担当者名が「森田 陽菜(イ」で切れる/保存ボタンの文字が2行になる | 選択欄は名前だけにして役割は横の印で出す。保存ボタンは「保存する」だけにし、足りない欄は上に小さく「あと:温度感」と出す |
| README のスクショが空欄 | Playwright で3枚撮って `docs/images/` に置いた(`npm run screenshots`)。見本データの画面と注記 |

直す途中であったこと:
- 適用済みのマイグレーションに、前の作業で説明のコメントを書き足していた。Prisma が「適用後に書き換えられた」と止めたので、**足したコメントだけを外して元の内容に戻した**(チェックサムが一致することを確かめた)。説明は schema.prisma の注記と 03 に置いた
- 既に行がある表に NOT NULL の列を足すマイグレーションは、Prisma が対話での確認を求めて作れなかった。**SQL を手で書いた**(空を許して足す → 既存の行を埋める → NOT NULL にする)。そのあと差分が無いことを確かめた
- 同じフォルダで別の dev サーバー(制作者側の確認用と思われる)が動いていて、画面テスト用の dev サーバーが起動できなかった。止めずに、画面テストを build した本番の形で動かすように変えた
